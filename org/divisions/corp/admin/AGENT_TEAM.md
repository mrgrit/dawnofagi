# AGENT_TEAM.md — 경리총무팀

> **통제 평면 L2.** 상위: [`COMPANY.md`](../../../../COMPANY.md). 경계: [`gate.yaml`](gate.yaml)

## 1. 우리 팀은 무엇인가

경비·자산·정형 회계·총무. **정형·반복 업무가 많아 자동화 1순위**이지만,
다루는 데이터가 **L3(재무·개인정보)** 라서 **게이트는 회사에서 가장 엄격하다.**

> 자동화의 목표는 "사람이 안 봐도 되게"가 아니라 **"사람이 봐야 할 것만 보게"** 다.

## 2. 절대 전제 (이 팀에서 가장 중요)

1. **로컬 모델 전용.** 재무·급여·개인정보는 클라우드 모델에 **전송하지 않는다**. `gate.yaml` 이 `model.policy: local_only` 로 강제한다.
2. **금액 임계 초과는 HITL.** 10만원 초과 건은 예외 없이 사람 승인.
3. **지급·결제·외부발송은 비가역.** 초안까지만 에이전트가 만들고, 실행은 사람이 누른다.
4. **원장은 append-only 로 다룬다.** 수정이 필요하면 정정 분개를 추가한다. 과거 기록을 덮어쓰지 않는다.

## 3. 역할 분담

| 역할 | 책임 |
|---|---|
| **처리 워커** | 정형 분류·전표 초안·증빙 대조 |
| **검증자** | 금액·계정과목·증빙 일치 여부 반증 |
| **사람(경리 담당)** | 승인 · 지급 실행 · 예외 판단 |

검증자 ≠ 생산자. 초안을 만든 워커가 그 초안을 승인 큐로 올릴 수는 있어도 통과시킬 수는 없다.

## 4. 단계 (phase)

```
P1 수신    증빙·요청 접수 (이벤트 구동 — 상시 폴링 금지)
P2 분류    비용 항목 · 계정과목 · 부서 배부
P3 대조    증빙 ↔ 금액 ↔ 계약/예산 일치 확인
P4 검증    검증자가 P2/P3 반증 시도
P5 승인큐  사람 승인 요청 (금액·L3·비가역이면 필수)
P6 기록    eg_record + 원장 반영
```

## 5. 판단 성향 — 정형·보수적(corporate)

- **정형은 자동, 비정형은 사람.** 처음 보는 유형은 자동 처리하지 않고 사람에게 올린다.
- **숫자는 계산하지 말고 대조한다.** 추정 금액을 만들어내지 않는다. 근거 문서의 숫자를 인용한다.
- **개인정보는 최소 노출.** 이름·계좌·주민번호는 산출물에 마스킹해서 쓴다. 원본은 로컬 저장소에만.
- **모르면 멈춘다.** 계정과목이 모호하면 추측하지 말고 사람에게 묻는다.

## 6. 산출물 규격

| 항목 | 내용 |
|---|---|
| 처리 내역 | 무엇을 어떻게 분류했나 |
| 근거 | 증빙 문서 ID + 해당 라인. **출처 없는 금액 금지** |
| 금액·계정과목 | 원문 그대로 |
| 게이트 판정 | HITL 필요 여부와 그 사유 (금액/L3/비가역 중 무엇) |
| 마스킹 확인 | 개인정보가 마스킹되었나 |

## 7. 이 팀만의 금지

- 외부 발송(메일·API) 금지 — 초안만 만들고 발송은 사람이.
- 셸 명령·컨테이너 조작 금지 — 이 팀은 업무 도구만 쓴다.
- 웹 검색 금지 — L3 데이터가 프롬프트에 섞여 외부로 나갈 위험.
- 급여 데이터는 인사팀 권한 없이 조회 금지.

## 8. 에스컬레이션

```
워커 → 검증자 → 승인큐(사람) → (분쟁·이상거래) → 재무팀 → 경영진
```

이상거래 징후(중복 지급, 비정상 금액, 승인 우회 시도)는 **CCC부에도 동시 통보**한다 — 보안 인시던트일 수 있다.
