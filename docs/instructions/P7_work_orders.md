# P7 — 작업 지시 파이프라인 (접수 → 결재 → 환경 → 착수 → 검수 → 정산)

## 목표

**외부/내부에서 업무 요청이 오면 알아서 환경이 만들어지고 관련 에이전트가 일한다.**

지금까지(P0~P6)는 *이미 정해진* 에이전트가 *이미 정해진* 업무를 한다. P7 은
**요청이 조직·인프라·에이전트를 만들어 내는** 경로다. 회사가 스스로 확장한다.

```
접수 → 분류·견적 → 결재 라인 → 인프라 준비 → 에이전트 편성 → 착수
     → 단계별 검수 → 종료·정산 → 기록(문서·일지·보고서)
```

- `COMPANY.md` §6 (자율화·HITL), `docs/context/01_aoc_architecture.md`
- `docs/governance/CONTROL_PLANE.md` (L1~L4 + 게이트 · 단조 축소)
- `docs/governance/PORTAL_GUIDE.md` (사람이 개입하는 통로)
- P6 `ops/dawn_ops/tenant.py` 의 `ONBOARDING_STEPS` — 고객 온보딩 8단계가 이 파이프라인의 원형이다

**없는 것 = P7 이 만들 것:**

1. **작업 지시(WorkOrder) 도메인** — 문의는 "물어봄", 작업 지시는 "실행 단위"다
2. **결재 라인** — 지금 승인 큐는 도구 1회용. 조직 계층 결재(팀장→본부장→대표)가 없다
3. **사람 역할(본부장·대표이사)** — 레지스트리가 에이전트만 안다
4. **인프라 프로비저닝** — 컨테이너/서버 준비
5. **에이전트 동적 편성** — 매니페스트 생성 + 게이트 컴파일
6. **단계별 산출물 검수 게이트**
7. **상시 작업 스케줄** — 보안관제·시스템운영
8. **기록 자동 생성** — 일지·보고서·정산

## DoD

### DoD-1 — 작업 지시 도메인과 두 접수 경로

`biz` 에 `work_order` 를 추가한다. 문의(inquiry)와 **분리한다** — 문의는 대화이고
작업 지시는 실행 단위다. 문의가 작업 지시로 **승격**될 수 있다.

```
상태: 접수 → 검토 → 결재대기 → 승인 → 준비 → 진행 → 검수 → 완료
                              ↘ 반려                    ↘ 반려(재작업)
```

| 필드 | 뜻 |
|---|---|
| `origin` | `external`(홈페이지 고객) / `internal`(그룹웨어 직원) / `standing`(상시) |
| `requester` | 외부는 고객 id, 내부는 그룹웨어 계정 |
| `division` | 담당 본부 — 결재 라인이 여기서 나온다 |
| `work_domain` | `work/<도메인>` — 어느 SOP 를 쓰나 |
| `risk` / `zone` | 어느 존에서 도는가 → 프로비저닝·게이트 결정 |
| `infra_tier` | **요청자가 접수 폼에서 고른다** — `none`/`container`/`vm`/`server`. 선택지는 그 사업의 `infra.allowed` 로 제한되고, 기본값은 `infra.default` 가 미리 선택된다 |
| `parent_id` | 하위 작업 (분해된 단계) |

**접수 경로 둘 다 같은 도메인에 쓴다.** 홈페이지는 인증 없이 `external`,
그룹웨어는 로그인 계정으로 `internal`.

**검증**: 홈페이지 폼 → 작업 지시 생성 → `dawn-biz orders` 에 보인다.
그룹웨어 폼 → 같은 결과. 테넌트 격리 유지(자사 = #0).

### DoD-2 — 결재 라인 (본부장·대표이사는 사람)

레지스트리에 **사람 역할**을 넣는다. 지금은 에이전트만 안다.

```yaml
# org/company.yaml (신규)
ceo:
  role: 대표이사
  portal_user: <그룹웨어 계정>

# org/divisions/<본부>/division.yaml (추가)
lead:
  role: 본부장
  portal_user: <그룹웨어 계정>
```

**결재 단계는 규칙에서 파생한다 — 사람이 매번 정하지 않는다.**

| 조건 | 결재 라인 |
|---|---|
| 기본 | 담당 **본부장** (사람) |
| + 신규 인프라 프로비저닝 | **대표이사** 추가 |
| + L3 자산 관여 (인사·재무·PII) | **대표이사** 추가 |
| + 외부 고객 계약 | **대표이사** 추가 |
| + 비가역 행동 포함 | **대표이사** 추가 |
| 상시 작업(`standing`) | 최초 등록 시 1회. 이후 자동 |

`auth.can_approve` 의 조직 트리 순회를 재사용한다 — **승인자는 그 작업의 본부
트리 안에 있어야 한다.** 결재는 순차(본부장 → 대표)이고, 어느 단계든 반려하면 멈춘다.

**검증**: 결재 라인이 규칙에서 나온다(하드코딩 아님). 트리 밖 사람은 승인 못 한다.
승인·반려가 감사 로그에 남는다. 재판정 불가(감사 추적).

### DoD-3 — 인프라 준비 (풀에서 할당)

**프로비저닝은 "만드는 것"이 아니라 "준비된 것을 꺼내 쓰는 것"이다.**
하드웨어·OS 설치는 사람이 미리 해 두고 `infra/pool.yaml` 에 등록한다.

이게 중요한 이유:
* 에이전트가 **클라우드 크레덴셜을 쥘 필요가 없다** — 과금 발생 행동이 없다
* 실패 모드가 "생성 실패"가 아니라 **"가용 자원 없음"** 이다. 훨씬 다루기 쉽다
* 회수 = **반납**이지 삭제가 아니다

| 등급 | 어디 | 어떻게 |
|---|---|---|
| `none` | 기존 환경 | 아무것도 안 한다 (진단·리포트 등) |
| `container` | **이 호스트의 el34 인프라** | 도커 컨테이너 + 존 네트워크 `el34-<zone>` |
| `vm` | **외부 시스템** (L2 연결) | 풀에서 `kind: vm` 할당 |
| `server` | **외부 시스템** (L2 연결) | 풀에서 `kind: server` 할당 |

**등급은 접수 시 요청자가 고른다.** 선택지는 그 사업의 `infra.allowed` 로 제한된다
(`org/businesses/*.yaml`). 사업이 허용하지 않은 등급은 폼에 나오지 않는다.

**고른 등급이 결재 라인을 올린다**: `container` 이하는 본부장, `vm` 이상은 대표이사
— 외부 시스템 자원을 점유하는 것이기 때문이다.

할당 실패(풀에 available 없음)는 작업 지시를 **`준비대기`** 로 멈추고 사람에게 올린다.
장비를 추가하거나 다른 작업이 반납하면 이어서 돈다.

**미해결 — 존 매핑** (Q10): 컨테이너는 도커 브리지(10.20.30~40.0/24), 외부 호스트는
물리 LAN(192.168.0.0/24) 이다. 같은 존 이름을 써도 **L3 경로가 다르다.** 외부 호스트가
컨테이너 존에 닿아야 하면 이 호스트를 경유하는 라우팅이 필요하다.

**절대 규칙**: 할당·반납 모두 **비가역 행동**이다. 승인 없이 집행하지 않는다.

**검증**: 승인 없이 할당되지 않는다. 사업이 허용하지 않은 등급은 거부한다.
존이 틀리면 거부한다. 풀이 비면 `준비대기` 로 멈춘다(실패가 아니다).
작업 종료 시 반납되고, 반납 실패가 케이스로 올라온다.

### DoD-4 — 에이전트 편성 (동적 생성)

작업 지시에 필요한 에이전트를 **매니페스트로** 만든다. 코드 생성이 아니다.

```
org/agents/<work-order-id>-<role>/
  agent.yaml     소속 팀 · 페르소나 · 선언 도구 · 존
  SOUL.md        L4 — 이 작업에서 나는 누구인가
  gate.yaml      이 작업으로 좁힌 경계 (단조 축소 — 팀 게이트를 넘을 수 없다)
```

**하네스·루프는 새로 짜지 않는다.** P2 의 워커 루프(①eg_search →②preview →③gate·run
→④eg_record)와 오케스트레이터(`phase`/`depends_on`)를 그대로 쓴다. P7 이 만드는 것은
**배치(누가 무엇을 어떤 순서로)** 이지 실행기가 아니다.

hand-off vs 병렬은 오케스트레이터가 이미 안다:
- `depends_on` 이 있으면 hand-off (앞 단계 산출물을 받는다)
- 없고 `check_separation` 이 통과하면 병렬

**검증**: 생성된 에이전트가 `make registry` · `make control-lint` 를 통과한다.
게이트가 팀 경계를 **넓히지 못한다**(단조 축소). 작업 종료 시 회수된다.

### DoD-5 — 착수·단계별 검수

```
착수 → 단계 산출물 → 검수 게이트 → 다음 단계
```

검수는 세 겹이다:
1. **기계** — 산출물 형식·필수 항목 (SOP 의 DoD)
2. **judge** — 근거·완결성·경로 (P3 품질 축 재사용)
3. **사람** — 위험도가 높거나 judge 가 fail 이면 결재 라인으로

**검증**: 검수를 통과 못 한 산출물로 다음 단계가 시작되지 않는다.

### DoD-6 — 상시 작업 (보안관제·시스템운영)

`origin: standing` 작업 지시. 최초 1회 결재 후 **스케줄로 돈다.**

| 예 | 주기 | 담당 |
|---|---|---|
| 알럿 트리아지 | 이벤트 발생 시 | `ccc-soc-triage-01` |
| 관제 1회전 (수집·탐지·판정) | 15분 | AOC |
| KPI·자율화 검토 | 주 1회 | 경영관리 |
| 인시던트 리허설 | 월 1회 | 사람 + 에이전트 |

**상시 작업도 작업 지시다** — 기록·보고서가 똑같이 남는다. 다른 점은 결재가 1회뿐.

### DoD-7 — 기록 (문서·일지·보고서·정산)

작업 지시 하나가 끝나면 자동으로 남는다:

| 산출물 | 어디 | 근거 |
|---|---|---|
| 작업 일지 | `document` (kind=`worklog`) | 트레이스 · 단계별 산출물 |
| 완료 보고서 | `document` (kind=`report`) | 산출물 + judge 판정 + KPI |
| 정산 | `expense` / 계약 연동 | 토큰·시간·인프라 사용량 |
| EG 축적 | `Task`/`Finding` 노드 | ④ eg_record 가 이미 한다 |

**전문 업무는 새 시스템으로.** 그룹웨어가 다루기 어려운 것(예: 독자모델 개발의
실험 관리, 대학 AX 컨설팅의 진단 리포트)은 `biz/` 에 모듈을 붙인다 —
P5 가 문서·CRM·프로젝트·경리를 붙인 것과 같은 방식이다.

`scripts/verify-p7.sh`

5. 작업 종료 후 컨테이너·에이전트가 회수된다 (누수 0)
6. 상시 작업이 결재 1회로 계속 돈다
7. 병렬 배치가 같은 자산을 동시에 건드리지 않는다 (`check_separation`)

### 자원 전제

`vm`·`server` 는 **외부 시스템에 미리 준비된 장비**다 (하드웨어·OS 설치 완료, L2 연결).
이 호스트는 `container` 만 담당한다. 개발 시스템은 2배 스펙으로 이관 예정이라
용량은 제약이 아니다 — 다만 **풀이 비어 있으면 `준비대기`** 이므로 장비를
`infra/pool.yaml` 에 등록하는 것이 선행 조건이다.
